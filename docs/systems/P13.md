Wave 6, lane B (beside P11a). Branch `pkg/P13`. Plan: `docs/plans/M2_M5_PLAN.md` §3.15, with the
contracts in §2.3 (ids and flags), §2.4 (quest, dialogue, tutorial and slice events), §2.7.4

## What was built

- **Three record types** with their schema modules: `quest`, `dialogue` and `tutorial_prompt`
  (`scripts/core/schemas/{quest,dialogue,tutorial_prompt}_schema.gd`).
- **QuestConditions** (`scripts/quests/quest_conditions.gd`): the pure evaluator of the §2.8.3
  condition shapes over a context dictionary.
- **The Quests autoload** (`scripts/quests/quests.gd`, after GameSession): data-driven quests with
  ordered stages, start conditions, abandonment and once-only rewards; the running dialogue
  session; the tutorial director; objectives for the HUD and the Valley bot; the end of the slice.
- **DialogueSession** (`scripts/quests/dialogue_session.gd`): one conversation (entry nodes,
  visible choices, effects with once-gated rewards).
- **TutorialDirector** (`scripts/quests/tutorial_director.gd`) and **TutorialText**
  (`scripts/quests/tutorial_text.gd`, the `{placeholder}` table).
- **NpcTalker** (`scripts/world/npc_talker.gd`): an Interactable that requests a conversation.
- **Screens**: the dialogue screen (`ui/screens/dialogue_screen.gd`) and the end screen
  (`ui/screens/end_screen.gd`).
- **HUD widgets**: the quest tracker, the objective marker and the tutorial prompt
  (`ui/hud/{quest_tracker,objective_marker,tutorial_prompt}.gd`).
- `project.godot`: the `Quests` autoload between GameSession and Sim (the only hotspot edit).

No shipped data: the quest line, the elder's dialogue and the 13 prompts are P15's
(`data/quests/`, `data/dialogue/`, `data/tutorial/`). Until then the Valley runs with quests on and
nothing to run. Tests use in-memory fixtures (`tests/support/quest_fixtures.gd`).

**Quest state** lives in WorldState flags, so checkpoints save it and reloads roll it back with
everything else: `quest.<short id>.stage` (the current stage; it keeps the last one after
completion) and `quest.<short id>.done` (true when complete, false when abandoned); the short id is
the id without `quest.` (`quest.main` → `quest.main.stage`, `reward.main.<stage>`).

**Evaluation.** A Sim POST_RESOLVE hook (order 100) evaluates every 10 ticks and on the tick after
a relevant event (`flag_changed`, `entity_died`, `object_destroyed`, `object_opened`, items,
areas, `encounter_cleared`, growth, level, weapon, `dialogue_outcome`, a counted hit). Each pass
loops until nothing changes (at most 64 changes), restarting from the main quest after every
change, so goals reached early complete in the same pass as their stage comes up. Nothing happens
while the player is dead.

- An inactive quest starts at once when `auto_start` (New Game: WorldState is empty), otherwise the
  first time all `start_conditions` hold: `quest.<q>.stage` = the first stage and `quest_started`
  (no `quest_stage_changed` for the first stage; see decision 19).
- An active quest whose `abandon_when` holds is abandoned: `quest.<q>.done = false`,
  `quest_abandoned`, no reward.
- When the current stage's `complete_when` holds: `try_set_flag("reward.<q>.<stage>")` grants the
  rewards once - items (`WorldState.add_item(..., "quest:<id>:<stage>")`), `set_flags`
  (`try_set_flag`) and XP (`Events.xp_award_requested(xp, "quest:<id>:<stage>")`) - then the next
  stage starts (`quest_stage_changed`; GameSession checkpoints `quest.main` stages).
- After the last stage: `quest.<q>.done = true`, `quest_completed`, then `on_complete_flags`
  (`try_set_flag`). The main quest's completion also calls
  `GameSession.request_checkpoint("quest_complete")`.
- When the flag `slice.completed` becomes truthy (any writer) while quests are active,
  `slice_completed` is emitted; on `slice_completed` Quests requests the end screen
  (`ui_screen_requested("end", end_summary())`).

**Level memory** (reset when a new player instance appears - a level load or reload - on
`checkpoint_loaded`, and by `reset_for_tests`): areas entered, deaths and destructions seen, and the
`hits_on` counters: the player's blows (attacker = the player's entity id) whose outcome connected
(HIT, BLOCKED, PARRIED, GUARD_BROKEN), per target and action id, with the action's kind.

**Objectives.** `objective_for(id)` = `{"quest_id", "stage_id", "text" (the stage's objective),
"kind" (the complete_when type), "marker_id", "position" (the marker's, else the first target found:
a living Sim entity, an area trigger, a breakable prop with that world_id; `Vector3.INF` when none),
"targets" (`QuestConditions.targets_of`), "bot" (the stage's hint, a copy), "title" (the quest's
display_name), "main", "stage_index", "stage_count"}`. Side quests are ordered by
`tracker_priority` (higher first), then quests started by conditions before auto-started ones,
then id descending - a village branch, then `quest.village`, then `quest.tutorial`. Marker, area
and prop positions are cached per level (a miss is retried once per second).

### QuestConditions (`class_name QuestConditions`, static, pure)

```gdscript
const KEYS := ["flags", "deltas", "inventory", "stage", "level", "weapon", "inside", "entered",
	"died", "destroyed", "hits", "hit_kinds"]
static func empty_context() -> Dictionary

static func truthy(v) -> bool; static func flag_matches(value, c) -> bool; static func same_value(a, b) -> bool
static func is_entered(ctx, area) / is_killed(ctx, id) / is_destroyed(ctx, id) -> bool
static func hit_count(ctx, targets, action_kind, action_id) -> int
static func targets_of(c) -> PackedStringArray
static func encounter_flag(encounter_id) -> String     # encounter.<short>.cleared (= the director's)
static func outcome_flag(dialogue_id, outcome) -> String   # dialogue.<short>.outcome.<outcome>
```

| Type | Holds when |
| --- | --- |
| `flag {flag, equals?, at_least?}` | equals (numbers compare as numbers), at least (a number), else truthy (true, non-zero, non-empty) |
| `entered {area}` | the player is inside now, or entered it since the level loaded |
| `killed {targets}` | every target has a saved kill (`deltas[id].killed`) or was seen dying |
| `encounter_cleared {encounter}` | `encounter.<short>.cleared` is truthy |
| `destroyed {world_id}` | `deltas[id].destroyed`, or its destruction was seen |
| `has_item {item, count}` | at least `count` held |
| `hits_on {targets, count, action_kind?, action_id?}` | the player's counted blows on the targets whose action matches both filters reach `count` |
| `stage_at_least`, `level_at_least` | the growth stage / the progression level (`player.progression.level`) |
| `weapon_equipped {weapon}` | the equipped weapon's id |
| `dialogue_outcome {dialogue, outcome}` | the outcome's flag is set |
| `all` / `any` `{of: [...]}`, `not {of: {...}}` | as named; malformed or unknown conditions never hold |

- The start node is the first entry whose conditions hold. A choice is offered while its
  conditions hold and its `take_items` are held; a node with none offers an implicit `[Leave]`.
- `choose(i)`: `once_flag` gate (`try_set_flag`); `set_flags` with `try_set_flag`; `outcome` →
  `try_set_flag(dialogue.<short>.outcome.<outcome>)` and `dialogue_outcome`; if the gate opened:
  `take_items` (each time when there is no once_flag), and with a once_flag the rewards -
  `give_items`, `xp` (`xp_award_requested(xp, "dialogue:<id>")`) and `learn_abilities` (the
  learner: `player.progression.learn_ability(id, "reward")`). Then `next`, or the end when it is
  `""`, names no node, or `effects.close` is set (`end_reason` "done"; the implicit leave: "left").

## Decisions and deviations

1. **Doc name.** `docs/systems/P13.md` (the task and §1.1 item 5); §3.15 names
   `P13-quests-dialogue.md`.
2. **Extra files**: `scripts/quests/tutorial_text.gd` (the placeholder table shared by the schema,
   the director and the widget), `tests/support/quest_fixtures.gd` (in-memory fixtures and the
   scoping helper) and `tests/slow/test_valley_quests.gd` (the wave notes ask for Valley-level
   tests in `tests/slow`).
3. **`entered` differs by user.** For quests and dialogue it holds while the player is inside the
   area **or** once it entered it since the level loaded: a quick run through an area between two
   evaluations is not lost, and a goal reached early completes when its stage comes up (§4.5). For
   tutorial triggers it is presence only, as §2.8.3 states (it combines with `min_stage` after
   growing inside the area). The memory resets on a reload; the stage flags are what persists.
4. **Kills and destructions** read the saved deltas (director members with `persist_death`,
   persistent props) and also the deaths and destructions seen since the level loaded, so actors
   that are not persisted (tests, tools) count too.
5. **Dialogue outcomes persist as flags** `dialogue.<short id>.outcome.<outcome>` (first write
   wins), which the `dialogue_outcome` condition reads; §2.3 lists only `dialogue.elder.met` in that
   domain.
6. **Id prefixes are enforced** (`quest.`, `dialogue.`, `tutorial.`), because the flags derive from
   the ids (`quest.<q>.stage`, `reward.<q>.<stage>`, `dialogue.<d>.outcome.*`, `<prompt>.seen`).
7. **Choice visibility includes `take_items`**: a choice that hands over items is offered only
   while they are held. A node with no choice to offer gets an implicit `[Leave]`, so a
   conversation never dead-ends. `take_items` follow the once_flag when there is one; `close` ends
   the conversation after its choice.
8. **Rewards need a once_flag** (a schema error otherwise), so dialogue XP, items and abilities are
   granted once ([spec §14]). Outcome events and `set_flags` (first write wins) are not rewards.
9. **The main quest's completion is a checkpoint.** GameSession checkpoints `quest.main` stage
   changes; the last stage completes the quest without a stage change, so Quests requests one
   (reason `quest_complete`). It is drained in the same tick's POST_RESOLVE (order 200, after
   Quests' 100), before the end screen opens, so "Quit to title" from the end screen keeps the
   completed slice.
10. **The end screen opens on `slice_completed`** (from any emitter, while quests are active), and
    Quests emits `slice_completed` when the flag `slice.completed` becomes truthy (the main quest's
    `on_complete_flags` in P15's data).
11. **Side-quest order** (tracker and objectives): the optional `tracker_priority`, then quests
    started by conditions before auto-started ones, then id descending. Without any
    `tracker_priority` this already puts a village branch before `quest.village` before
    `quest.tutorial`, as §3.15 asks.
12. **Tutorial details the plan leaves open.** Higher `priority` wins (ties: the lower id); an event
    trigger stays pending 6 s; the seen flag is set on dismissal, not on show (a reload while a
    prompt is up shows it again, and a lesson cannot be lost); `sets_flag` is set only when the
    lesson is done (the dismiss condition, including the `timeout` type, whose time is the lesson),
    not on a `timeout_s` fallback; a prompt whose flag dismissal already holds is completed
    silently; dismiss shapes `{"type": "action_kind", "action_kind", "count"}`, `{"type":
    "action_id", "action_id", "count"}`, `{"type": "event", "event", <filters>, "count"}`,
    `{"type": "flag", "flag", "equals"?, "at_least"?}`, `{"type": "timeout", "timeout_s"}`, each
    with an optional `timeout_s` fallback.
13. **`hits_on` counts only the player's blows** that connected (HIT, BLOCKED, PARRIED,
    GUARD_BROKEN), per target and action id.
14. **Dialogue is not gated** by `is_active()`: a talker in the sandbox would work; quests,
    tutorials and the end screen are.
15. **Test seams** (reset by `reset_for_tests`): `Quests.test_active`, `Quests.scope`,
    `Quests.main_quest_id` and `Quests.tutorial.scope`, so fixtures run apart from the quests and
    prompts P15 ships. `QuestFixtures.activate(quest_ids, prompt_ids, main_id)` sets them.
16. **`interact_id` of a talker** is its npc id, so `Events.interacted` names the NPC.
17. **A talk that cannot start** (no record, or no entry holds) posts "They have nothing to say
    right now." and opens nothing.
18. **The tracker's pacing line** shows for XP from `prototype_pacing` quests and from dialogue
    rewards (decision 7 labels quest-line XP); the XP bar (P12) keeps its own "+N".
19. **A quest's start emits `quest_started` only**, not `quest_stage_changed` for its first stage:
    GameSession checkpoints every `quest_stage_changed` of `quest.main`, and New Game, where
    `quest.main` starts, has just committed its own checkpoint. A second one there is redundant and
    breaks P06's `test_a_failed_write_warns_and_play_continues` (exactly one write attempt at New
    Game) as soon as a `quest.main` record exists - found by running the whole suite against
    temporary P15-style records (not committed).

### A fallback timeout lost the lesson

- **Finding.** P15 gave every prompt that waits for an action a `timeout_s` fallback, so an
  ignored lesson cannot hold back every later prompt. But a fallback dismissal set only
  `<id>.seen`, and a seen `once` prompt never shows again, so nothing could set its lesson flag any
  more. `quest.tutorial`'s `awaken` stage completes only on `tutorial.camera.done`: a player who
  looked around the Cradle for 45 s first could toggle the camera as often as they liked, and the
  tracker kept "Look through the giant's eyes (V), then step back" until the tutorial was
  abandoned at the Grove (the reviewer: New Game, 46 s, two toggles, 20 ticks: still `awaken`).
  The same held for `tutorial.block` (`tutorial.dodge` requires its flag, `spar` needs both) and
  for the dummies' chain (`heavy`, `footfall` and `lock` trigger on the previous lesson's flag).
- **Fix** (`scripts/quests/tutorial_director.gd`). A fallback takes the prompt away, not its lesson.
  A lesson is open while its prompt is seen, its `sets_flag` is not set and its dismissal is an
  action, an event or a flag (`lesson_open`). The director keeps counting an open lesson's
  dismissal without showing the prompt: the same matching as the shown prompt's
  (`dismiss_matches`), on from the prompt's progress when the fallback took it (a toggle made while
  it showed still counts). When the count is reached, or a flag lesson's flag holds, it sets
  `sets_flag` and nothing else: no `tutorial_shown` / `tutorial_dismissed`, and the prompt never
  shows again. Everything that waits for the flag follows by itself: the quest stage (Quests sees
  the flag change), a prompt with that flag as trigger or `requires_flags`. Open lessons follow the
  saved flags; their counts are level memory (`reset()` clears them, like `hits_on`), so after a
  reload an open lesson counts from zero. Data, quests and the plan's prompt fields are unchanged.
  Plain timeout prompts (soldier guard, boss charge) are done by their time and never open.
