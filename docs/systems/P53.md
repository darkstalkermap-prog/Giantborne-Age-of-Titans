# P53 — The look record v2: slots, sliders, migration, and `GiantLook` by slot

Plan: `docs/plans/M11_PLAN.md` §3.6 (and §1.1, §1.5-§1.7, §2.5, §2.6, §2.11, §2.13, §0.3's record row, §0.4
decisions 7, 10, 11). Wave W31, lane B, beside P52 (the 0.11.0-m11 release). Built on 19 November 2026 on `pkg/P53`
from the tag `m11-gate-a2`; the version stays the release's (P53 ships in 0.12). Every number here was taken on the
shared container (4 CPUs, no GPU: llvmpipe natively), the other lane's release checks running beside it; the loads
are given where they matter.

The goal: the record, its migration and the look path at version 2, complete and shippable on M10's ten garments,
so that the wardrobe (P54) and the creator II (P55) only add content and screens. A player who changes nothing
plays and saves as in 0.11: a character without a look still captures none, the default look draws the same
meshes in the same colours, and the soak is unchanged (see "Checks").

## What was built

### 1. The oracle (`tests/support/appearance_v1_oracle.gd`)

M10's `Appearance` (`scripts/progression/appearance.gd` at `5ff50f0`, which `m11-gate-a2` still had unchanged),
copied whole; only its first line (`class_name Appearance`) is replaced by three comment lines saying so (two
classes of one name cannot exist). Never edited. It reads this build's data: the sets keep every M10 field it reads
(the outfits keep their M10 `garments` list for it), and this build's presets, being version 2, read to it as a
later build's, so its default falls back to its own `FALLBACK_RECORD` (M10's Wanderer) - exactly what the
migration's inputs need. M10's eight preset records are kept as they shipped in
`tests/fixtures/appearance/m10_presets.json`.

### 3. `GiantLook` by slot (`scripts/presentation/giant_look.gd`, `giant_model.gd`, the shaders)

- **Garments as `{mesh, dye, kind}`**: `garment_meshes(index, look)` resolves an entry's `mesh` - an index garment
  (its meshes in `index.garments`) or a garment mesh named directly (P54's single-part garments may be) - to the
  meshes shown with their dye; each mesh's cloth material takes its garment's dye, and a `kind` "metal" sets the
  cloth shader's `kind` 1. **M10's shape still draws as it did** (an index garment id with `dye_primary` /
  `dye_secondary` by each mesh's index `dye`): the tests' and probes' hand-made looks keep working.
- **`build`**: `giant_skin` and `giant_cloth` gain `uniform vec2 build` and `uniform float build_max_m`, and their
  vertex functions push `VERTEX += NORMAL * dot(COLOR.gb * 2.0 - 1.0, build) * build_max_m` (probe 2's line; at
  (0, 0) nothing moves). `apply` sets both on every skin and garment material when they change (the creator's
  every pick stays inside test_giant_preview's 1 ms; `build_materials` forgets the last values). The index's
  `build_max_m` (0.099254) is P48's.
- **The shadow proxy** (P48's follow-up): `GiantModel.apply_build(build, build_max_m)` gives the proxy a material
  whose vertex function is the same push the first time a build leaves (0, 0); the giant as built keeps the glTF's
  material, so a player who changes nothing compiles nothing new.
- **`face`**: every shown mesh with a blend shape named like a face key (`jaw`, `chin`, `nose`, `brow`, `cheeks`,
  `age`) takes the slider's value; a mesh without them is left alone, and a look without a face slider skips the
  meshes unless one was set before (then they go back to 0). No mesh has the keys yet (P56).
- **Accessories and beads**: the index categories `accessory` and `bead` draw with the cloth shader
  (`KIND_OF_CATEGORY`) and are shown when the look names them; `validate()` names unknown garments, accessories and
  beads. No content yet (P54, P56).
- **`paint`** as an Array of two: both designs placed in `region_paint`, one `paint_color` (the record has one
  paint colour). `paints(look)` reads either shape.
- **`DEFAULT_LOOK`** restated in the v2 shape with the Wanderer's values: the belt in dark leather and the braies
  undyed, build zero, the face at zero, no beads, no accessories, no paint.

### 4. The session and saves

- `ui/screens/shrine/appearance_tab.gd` needed no change: it shows `Appearance.summary_lines`, which reads the record
  v2 in M10's words for any look M10 could make.
- `CharacterState.sanitize` adds `Appearance.NOTE_MIGRATED` when the look was migrated; `SaveSlots.sanitize` (the
  one note) keeps it once: it sets the flag **`appearance.slots_seen`** in the document's world flags, and a
  document that has the flag loses the note. So the load says once: "Your giant's clothing is now worn piece by
  piece; nothing was changed." `tutorial.appearance_slots` (`data/tutorial/appearance_slots.json`) then points to
  the Appearance tab at the next shrine, once, dismissed by the tab or after 15 s.
- **Absent stays absent**: a character without a look captures none, adds no note and sets no flag
  (`test_save_migration`, `test_appearance_migration`, `test_appearance_session`).
- **A v1 record is rewritten only at a kept look or the next checkpoint**: a read migrates in memory and writes
  nothing; `PlayerAppearance` captures the sanitized record, so the next checkpoint writes version 2 with the flag
  (`test_save_slots`, `test_appearance_session`). `SaveSlots.SCHEMA_VERSION` stays 2.
- A version-3 record (a later build's) is kept byte for byte through a load and a checkpoint, and draws the default.

## Deviations

- **The index v2's fields for M10's garments are in the data, not the index.** The plan's dependency ("P48 ... the
  index's `slot` field for M10's garments") did not land: P48's index has no `slot`, `shell` or `material`, and W31
  has no asset writer. `set_garment.json` carries each garment's slot, material and index garment, which is all the
  record and the look need; P54 writes the index v2 (FOLLOWUPS).
- **`test_appearance_migration` is split**: the presets, the edges, the fixtures and the 26 broken shapes in the
  default tier (about 0.2-0.4 s), the rest of the matrix - a record per M10 option, every outfit in every dye pair,
  360 random M10 records - in `tests/slow/test_appearance_migration_matrix.gd` (about 0.7 s), inside the default
  tier's 0.8 s share only so.
- **The rendered build check is a slow suite of its own** (`tests/slow/test_build_render.gd` with
  `tests/support/build_render_probe.tscn`), a test file the plan's owned list does not name; it is the plan's test
  "the build push moves no landmark and changes the rear silhouette (rendered)".
- **The "26 broken shapes of the M10 gate"** were a reviewer's script, not in the repository; `test_appearance_
  migration.broken_shapes()` writes 26 of the kinds the gate's lens 4 named (a look that is not a record, wrong
  types in every block, versions that are not one) and 19 version-2 equivalents.
- **M10's "future" fixture** (`v2_appearance_future.json`, a `v: 2` with a skin block) now reads as a broken
  version 2 (the default look and its note). The later-build cases read `v2_appearance_v3_future.json`.
- **Edits to other packages' tests** (each because the record's contract changed, none loosening a check):
  `test_giant_look_real`, `test_giant_preview`, `test_secondary_motion`, `test_appearance_random`,
  `test_appearance_shrine` put an outfit on with `Appearance.with_outfit` (or a paint with `with_paint`) where they
  set `outfit.set` or `paint.design` by hand; `test_giant_look_real` resolves a look's garment entries by
  `Appearance.garment_id` and gained a test per garment; `test_shrine_appearance`, `test_shrine_appearance_saves`,
  `test_appearance_session` and `test_save_slots` read the later build's look from the version-3 fixture;
  `test_creator_mouse` names the dye rows by their v2 paths; `tests/support/appearance_random_check.gd` checks both
  paint places; `test_valley_content` knows the new prompt and its flag.

## Floors and tolerances changed

None loosened. Changed with the contract, each stated in its test:

- `test_appearance_record`: scars "unique, at most four" -> **at most six** (`MAX_SCARS` 4 -> 6, plan §2.5); "v 1.0
  is cast to the int 1" -> v 2.0 to 2; the later build's record `v 2` -> `v 3`.
- `test_appearance_schemas`: "thirteen sets" -> **16** (the record v2's three); "a preset of another record
  version: version 1" -> version 2.
- `test_giant_preview`'s "a whole look is applied in under 1 ms" is unchanged (it failed once at 1.044 ms under a
  load of 6 before the build's uniforms were set only on change; it passes since).
